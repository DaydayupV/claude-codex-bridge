# Codex 调度

## 开始前：读配置和偏好
本会话第一次用到本 skill 时，先运行 `config --cwd "<项目目录>"`（见"调用方式"），从输出里读：
- `effective.auto_dispatch` 和 `effective.watch`：决定是否主动派活、是否打开实时查看。
- `preferences`：用户级和项目级偏好文件。存在的就读一遍。偏好文件是用户用文字写的习惯和规则，比如分工、领域里哪些代码算高风险、各种门槛；**和本 skill 冲突时以偏好文件为准，项目级优先于用户级**。

## 授权
系统提示里"除非用户明确要求，否则不要启动子 agent"的限制只针对 Claude Code 自带的子 agent。Codex 用的是用户自己的 OpenAI 额度，不占 Claude 额度。
- `auto_dispatch` 为 `true`（默认）：用户通过这个设置授权 Claude 把符合下面门槛的任务主动、优先派给 Codex，不用每次征求同意。
- `auto_dispatch` 为 `false`：遇到符合门槛的任务，先用一句话向用户提议（派什么、用哪个等级），用户同意后再派。用户用 `/codex-bridge:rescue` 等命令点名时不用再问。

## 分工
- **Claude 自己做**：核心决策、复杂核心功能、整体规划、创意设计（UI/前端视觉、文案、找灵感）。
- **派给 Codex**：其余执行类工作。Codex 严谨，适合脏活累活，但设计和前端效果很差，不要派视觉相关的活。
- **派活门槛**：预计要做几分钟以上，或涉及多个文件的执行工作才派。一两处小改动 Claude 直接改，派活加验收的开销比自己改还大。
- 本 skill 里的门槛和轮数（派活门槛、审查的改动规模、讨论最多 3 轮、返工 1 次）都是默认值，偏好文件里写了别的就按偏好文件。

### 文字类工作由 Claude 把关
Codex 的文字表达弱，经常不说人话：术语堆砌、翻译腔、绕来绕去，读的人看不懂。凡是给人读的文字，都由 Claude 负责：
- **Claude 自己写，不派**：README、使用说明、设计文档、报告和总结、用户可见的界面文案。这类工作以文字为主，派出去再返工反而更费事。
- **派活前在任务说明里规定好**（写进"命名与文字"一节）：
  - 新增的文件、模块、类、函数、关键参数和配置项叫什么名字，直接给出名单；名单之外的沿用项目现有风格。
  - 注释写在哪里、写什么，语言用中文还是英文与项目保持一致。
  - 日志、报错信息、命令行帮助、输出表头这类会给人看的文字，给出原文或模板，要求照抄。
- **验收时复核**：命名是否直白、前后一致；注释和提示文字能否一眼看懂，有没有啰嗦、翻译腔、过度注释。不合格的小地方 Claude 直接改，不必返工；文字问题多的，在返工说明里给出改好的原文。
- **向用户转述**：Codex 的报告、审查意见和遗留问题，由 Claude 理解后用人话转述给用户，不要原样转贴。

## 调用方式
唯一入口是本 skill 目录下的 `scripts/codex-run.mjs`（即 `${CLAUDE_PLUGIN_ROOT}/skills/codex-dispatch/scripts/codex-run.mjs`）。不要手敲 `codex exec`。

- **没有例外**：测试、验收、试跑、一次性问答，也都必须走这个脚本。只读的问答用 `discuss`。插件带有钩子，直接调用 `codex exec` 或 `codex review` 的命令会被拦下。
- **遇到沙箱问题时停下来**：Codex 因为沙箱无法启动命令或报错时，把错误原文和你的判断告诉用户，由用户决定是否修改配置。不要自己换沙箱、改配置文件，也不要想办法绕开脚本。

```bash
node "<脚本路径>" run    --cwd "<项目目录>" --brief "<任务说明.md>" --title "<短标题>" --level <simple|normal|complex> [--add-dir "<目录>"] [--timeout 分钟]
node "<脚本路径>" resume --run <run_id|last> --brief "<返工说明.md>" --level <simple|normal|complex>
node "<脚本路径>" discuss --cwd "<项目目录>" --brief "<议题.md>" --title "<短标题>" --level <normal|complex>
node "<脚本路径>" review --cwd "<项目目录>" [--uncommitted | --base <分支> | --commit <sha>] [--brief "<审查重点.md>"] --level <simple|normal|complex>
node "<脚本路径>" status [--run <run_id|last>] [--limit n]
node "<脚本路径>" watch  [--run <run_id|last>]
node "<脚本路径>" config [--cwd "<项目目录>"]
```

- 模型、推理强度、沙箱、审批、超时由配置文件决定（见"配置"一节）；没有配置的项沿用 Codex 自己的 `~/.codex/config.toml`。
- 拿不准当前设置时先运行 `config --cwd "<项目目录>"`，它会列出实际生效的配置、记录目录和 watch 启动器的路径。
- 沙箱不是 `read-only` / `workspace-write` 时（比如 `danger-full-access`），Codex 能写任何目录，`--cwd` 只决定它从哪里开始工作，**不限制写入范围**。这时范围只能靠任务说明约束，再靠事后审查 diff 把关。
- 任务说明先写成 UTF-8 文件（有 scratchpad 目录就放在那里，否则放在系统临时目录），脚本会自动附加固定约束：不越界、只写必要测试、不 commit/push、不碰密钥、按 schema 汇报。
- **一律用后台方式运行**（Bash 的 `run_in_background`），跑完会自动通知。等待期间可以做别的，不要轮询。
- **每次调用 Codex（`run`、`resume`、`discuss`、`review`）都必须在对话里明确告诉用户用的是什么模型和推理强度**，例如"已派给 Codex：模型 gpt-6-astra，推理强度 max（等级 complex）"。以脚本启动时输出的第一行（"开始｜模型 …｜推理强度 …"）为准，不要凭配置自己推断；模型来自 Codex 配置时照实说明。最终汇报里再写一次。
- **启动 `run`、`discuss`、`resume` 后，下一步必须立即处理实时查看**（见"实时查看"一节），测试和小任务也不例外。用户要靠它看到 Codex 在做什么，漏掉就等于让用户干等。
- 结果以 JSON 打印到 stdout：`report`（Codex 的结构化报告）、`changes`（脚本实际追踪到的工作目录内改动）、`session_id`、`run_dir`。完整 diff 在 `run_dir/diff.patch`。
- 多个任务可以并行，但文件范围不能重叠。**Codex 正在改的文件，Claude 不碰。**

## 配置
配置文件是 JSON，按顺序叠加，后面的覆盖前面的：脚本内置默认值 → 用户配置 `~/.claude/codex-bridge.json`（可用环境变量 `CODEX_BRIDGE_CONFIG` 换路径）→ 项目配置 `<项目目录>/.claude/codex-bridge.json`。用户配置不存在时，脚本第一次运行（任何子命令）会自动生成一份：默认模型 `gpt-6.1-sol`，三种模式的复杂任务用 `gpt-6-astra`。脚本输出"首次使用，已生成配置文件"时，告诉用户生成了配置文件、在哪里、用了哪些模型，并提醒可以按需修改。

| 字段 | 作用 | 默认 |
|---|---|---|
| `auto_dispatch` | 是否主动派活（见"授权"） | `true` |
| `watch` | `auto`：派活后打开实时查看；`off`：不主动打开 | `auto` |
| `model` | 各等级没单独写模型时用的模型 | `null`，沿用 Codex 配置 |
| `levels` | `run` / `review` / `discuss` 三种模式下，`simple` / `normal` / `complex` 三级任务各自的 `{ "model", "effort" }`。`model` 为 `null` 时用顶层 `model`；`effort` 只能是 `low` `medium` `high` `xhigh` `max` `ultra` | 模型都是 `null`；推理强度 run 和 review 为 medium / high / max，discuss 为 high / max / max |
| `sandbox` | 三种模式各自的沙箱：`read-only` / `workspace-write` / `danger-full-access` | 全部 `null`，沿用 Codex 配置 |
| `approval` | 审批策略，如 `never` | `null`，沿用 Codex 配置 |
| `timeout_min` / `stall_min` | 总超时 / 卡死判定（分钟，`stall_min` 为 0 时关闭） | 240 / 20 |
| `codex_bin` | codex 可执行文件或 `codex.js` 路径（也可用环境变量 `CODEX_BIN`） | 自动查找 |
| `runs_dir` | 运行记录目录（也可用环境变量 `CODEX_RUNS_DIR`） | `~/.claude/codex-runs` |

- **Windows 上不要把 `sandbox` 设成 `read-only`**：Codex 的 Windows 沙箱在只读模式下可能连读文件的命令都启动不了。讨论和审查的只读要求靠脚本附加的规则约束，脚本事后也会检查有没有文件被改动。
- 项目配置只认 `model`、`levels`、`timeout_min`、`stall_min`。`levels` 可以只写要改的那几项，比如只改 `run.complex.model`。`auto_dispatch`、`watch`、沙箱、审批、可执行文件和记录目录只能写在用户配置里，以免克隆来的仓库给自己提权或擅自花用户的额度。
- 用户要改配置时，直接编辑对应的 JSON 文件，改完运行 `config` 确认生效。

## 实时查看（每次派活都做）
用后台方式启动 `run`、`discuss` 或 `resume` 之后，立即让用户能看到实时进度。`watch` 为 `off` 时跳过本节，只告诉用户可以用 `/codex-bridge:watch` 查看。

- **有 `run_in_terminal` 工具时**（Claude 桌面版），在用户的终端面板里打开：用 `run_in_terminal` 运行 `node <记录目录>/watch.mjs --run <run_id>`，标题写"Codex：<短标题>"。记录目录默认是 `~/.claude/codex-runs`，在 Windows 上写成 `C:\Users\<用户名>\.claude\codex-runs`，以 `config` 的输出为准。这个启动器由脚本自动生成，插件路径含非 ASCII 字符时也能满足 `run_in_terminal` 只接受 ASCII 的要求。
- run_id 在启动后后台输出的第一行（"记录目录 …/<run_id>"）里。不加 `--run` 时它会跟踪正在运行的任务，但其他会话可能也在跑任务，所以尽量指定。
- 打开后把标签页链接 `[Codex：<短标题>](#terminal/<tab_id>)` 发给用户。
- **没有 `run_in_terminal` 时**（比如命令行版 Claude Code），把完整的 watch 命令放在 bash 代码块里发给用户，请用户在另一个终端里运行。
- 任务结束后 watch 会自动退出，标签页保留，供用户回看。不要关闭它。
- 默认是简洁显示。用户要看完整细节时，加 `--verbose`。
- `review` 只在用户要求时才打开实时查看。

## 任务等级与推理强度
`run`、`resume`、`discuss`、`review` 每次都必须显式给出 `--level`，没有默认值，漏写脚本会直接报错。Claude 只判断任务属于哪一级，具体用哪个模型和推理强度由用户在配置的 `levels` 里决定，运行时会打印"模型 / 等级 → 推理强度"。

| 等级 | `--level` | 什么样的任务 |
|---|---|---|
| 简单 | `simple` | 目标和做法都明确，几乎不需要判断：按清单批量改名或替换、套用现成模式补齐同类代码、格式或目录迁移、跑现成脚本整理数据、单文件的小功能 |
| 常规 | `normal` | 大多数执行任务：按规格实现功能、写脚本和工具、原因已经清楚的 bug 修复、常规重构、补测试 |
| 复杂 | `complex` | 跨多个模块的改动；根因不明、需要排查的 bug；对数值或逻辑正确性要求高的代码，比如金额和计费计算、数据迁移、权限判断；性能优化；并发 |

- 拿不准时往高一级选。
- 审查（`review`）一般用 `normal`；审查高风险代码时用 `complex`。
- 用户点名要某个推理强度（比如"用 ultra 跑"）时，改用 `--effort <强度>` 直接指定，不再按等级换算，模型用顶层 `model`。`--level` 和 `--effort` 只能给一个。
- 用户点名要某个模型时，加 `--model <模型>`，它覆盖配置里的模型，可以和 `--level` 或 `--effort` 一起用。
- 续接时模型按新给的等级重新确定，所以返工升级时可能换成另一个模型；配置里哪里都没写模型时，沿用上一轮的模型。

## 写任务说明
说得越细，Codex 做得越好。按下面的结构写：

```markdown
# 目标
要做成什么，为什么做（一两句背景）。

# 范围
- 允许改动：具体文件或目录
- 只读参考：相关文件
- 不要碰：……

# 要求与约束
接口签名、数据格式、要沿用的现有模式和工具函数、性能要求、兼容性等。

# 命名与文字
- 命名：新增的文件、类、函数、关键参数和配置项叫什么名字
- 注释：哪里需要写，写什么
- 提示文字：日志、报错、帮助信息、输出表头的原文或模板（要求照抄）
（任务不涉及这些时可以省略本节）

# 禁止事项
本任务特有的禁区。

# 完成标准
怎样才算做完，需要跑哪些命令验证（给出具体命令）。

# 交付
需要在报告里特别说明的内容。
```

Codex 偏爱防御性编程，容易写大量多余的校验和测试。任务说明里要写明"只写必要的测试，不要过度防御"（脚本已自动附加，任务特别容易过度时再强调一遍）。

## 研究与分析类任务
研究类任务指结论要靠实验和数据支撑的工作，比如策略和因子研究、数据分析、方案对比实验、性能调查。这类任务的风险不在代码写错，而在结论超出了证据。

### 研究任务说明的检查清单
把研究派给 Codex 时，在上面的通用结构之外，任务说明还要包含下面几项。某一项不适用时，写明不适用和原因，不要直接省略。讨论阶段已经定下的问题和假设，直接写进来，不用重新讨论。
- **问题与假设**：要回答的问题；每条假设和它的判读标准。判读标准事先定好，不能看到结果再改。
- **对照组**：需要哪些对照和基准，各自回答什么问题。
- **稳健性**：怎么检验结论不是某个参数点或某段时间的偶然，比如参数邻域、时间段切分、换起点。
- **混淆因素**：列出可能干扰结论的因素，要求逐项排查或说明为什么不适用。常见的有：资金或规模路径（本金变化、整手限制）、样本曝光（看过结果后再选）、多重检验、幸存者偏差、数据口径变化。
- **统计判断**：怎么判断差异是否显著，比较多组时怎么校正。
- **交付**：每条结论对应的证据（文件、数字、可以复算的方法），以及没能验证的部分。

### 结论落地前的证据审查
研究结论写进长期档案、报告或文档，或者作为定论交给用户之前，不管研究是 Claude 做的还是 Codex 做的，都用 `discuss` 发起一次证据审查（`--level complex`，开新会话，不在做研究的那个会话里自审）：
- 议题说明逐条列出结论，每条附上证据的位置和关键数字。
- 要求 Codex 逐条判断：证据够不够支撑这条结论，有没有说过头，有没有没控制住的混淆因素，统计上站不站得住。
- Claude 按讨论模式逐条裁决，修正结论后再写入。已经写进档案的结论被推翻时，以追加修订的方式更正，不改原记录。

## 验收（每次必做）
1. 先看 `status` 和 `report.status`：不是 `completed` 就先读 `open_issues`。
2. 读 `run_dir/diff.patch`，并核对 `changes.files`：
   - 有没有改到范围外的文件；`report.files_changed` 和实际改动是否一致
   - 逻辑对不对，有没有过度防御、多余抽象、冗余测试
   - 命名、注释和提示文字是否符合任务说明，是否说人话（见"文字类工作由 Claude 把关"）
   - 只追踪工作目录内的改动；如果任务涉及工作目录外的路径，要另外检查
3. **实际运行验证**：跑构建、测试或脚本本身，不能只看 Codex 自己说"通过了"。
4. 确认无误后再向用户汇报。

## 返工与失败
- 不合格时用 `resume` 返工一次，在返工说明里写清楚哪里不对、要怎么改。原因是任务难度估低了的话，返工时把等级升一级（simple → normal → complex）。其余情况沿用原来的等级。
- 返工后还不合格，或者 Codex 超时、报错，由 Claude 自己接手完成，并告诉用户原因。
- 结果状态为 `stalled`（卡死：超过 20 分钟没有任何活动，且没有命令在执行，脚本已自动终止）时，多半是网络或服务的临时问题。用 `resume` 让它从断点继续一次；再卡死就由 Claude 接手。可以用 `--stall <分钟>` 调整阈值，`--stall 0` 关闭检测。总超时默认 240 分钟，用 `--timeout` 调整。
- 怀疑任务卡住时，先运行 `status` 看"最后活动 X 分钟前"和当前步骤，不要凭感觉判断。正在执行命令（比如跑大计算）时，长时间没有新事件是正常的。`interrupted` 表示调度进程已经不在了（比如会话或应用被关闭），这时 Claude 收不到完成通知，需要手动查看 `status --run <run_id>`，再决定是续接还是重来。
- `report.status` 为 `blocked` 时，先判断：属于 Claude 能决定的，补充信息后用 resume 继续；需要用户决定的，去问用户。

## 讨论模式（/codex-bridge:discuss）
遇到复杂的计划、方案或想法时，先和 Codex 讨论，不执行。**观点始终由 Claude 主导**：Codex 的意见只作参考，接受还是拒绝由 Claude 根据论据决定，不因为它坚持就让步。

### 什么时候自动开启
用户用 `/codex-bridge:discuss` 发起时直接开。自动开启必须**同时满足**下面三条，只满足一两条的不开：
1. **复杂**：涉及架构或多个模块，影响长期结构；或者是金额计算、数据一致性、权限和安全等关键逻辑的设计。
2. **不确定**：没有明显的最优解，有好几个可行方案需要权衡；或者关键假设还没验证。
3. **选错代价高**：选错了要大面积返工，或者会影响结果的正确性。

**用户只是来要建议、还没决定做不做时，同样按这三条判断。** 比如"有什么研究方向的建议""这个架构该怎么选"：满足三条就先讨论，再把裁决后的结论交给用户，不要自己直接给出答案。为了写议题说明，可以先读代码和数据、做只读的统计，把事实弄清楚。

普通的实现细节、已经有明确方案的任务、用户已经拍板的决定，都不开。自动开启时告诉用户一句："这个问题我先和 Codex 讨论一下。"

### 流程（最多 3 轮）
1. **第 1 轮，独立出方案**：用 `discuss` 发起。议题说明只写背景、要解决的问题、约束、已知事实、相关代码位置，以及要它回答的具体问题，**不写 Claude 自己的倾向**，以免它顺着说。在读 Codex 的结果之前，Claude 先把自己的方案写进一个文件（scratchpad 目录或系统临时目录），以免反过来被它带偏。
2. **第 2 轮，交叉挑错**：用 `resume --run <第 1 轮的 run_id>` 续接。把 Claude 的方案发给它，要求它找出最薄弱的地方，并和它自己的方案对比；同时 Claude 也写出对它的方案的质疑。
3. **第 3 轮（可选）**：只有关键分歧还没解决、并且多一轮确实可能改变结论时才做。
4. **Claude 裁决**：逐条决定接受还是拒绝 Codex 的观点，写明理由，形成最终方案。

- 讨论一般用 `complex`；议题不算特别复杂时用 `normal`。续接下一轮时沿用第 1 轮的等级。
- 讨论是只读的：Codex 可以读代码、跑只读命令来支撑观点，但不能改文件。脚本发现有文件改动会在 warnings 里报出来，这时要检查并还原。
- 讨论同样要处理实时查看。
- 需要用户决定的问题，比如偏好、业务取舍、风险承受度，不要替用户拍板，把选项和 Claude 的推荐一起交给用户。

### 向用户汇报：决策记录
不贴原始对话，用人话整理成：
- **议题**：一句话
- **候选方案**：Claude 的、Codex 的，各自的核心思路和取舍
- **Codex 的主要观点**：每条注明 ✅ 接受 / ❌ 拒绝 / ⚠ 部分接受，并写明理由
- **最终方案**：以及和 Claude 最初方案相比改了什么
- **待确认**：需要用户拍板或先验证的事
- 附上讨论的 run_id，方便用户回看原始记录

## 何时请 Codex 审查（/codex-bridge:review）
用户明确要求时直接做。否则按任务情况判断：

**值得审查**
- Claude 自己写的复杂核心功能，交付前用另一个模型做独立复核
- 高风险代码：金额和计费计算，数据删除和迁移，并发，鉴权和安全，不可逆操作
- 改动大（大约超过 300 行或 5 个以上文件），或者修了一个根因不明的 bug
- 研究结论写进档案或报告之前：用 `discuss` 做证据审查，见"结论落地前的证据审查"
- Codex 交付的高风险改动：用 `review` 发起一个**新会话**审查，不要让它在原会话里自己审自己

**不必审查**
- 小改动、文档、注释、样式、文案、纯配置
- 一次性脚本、原型，且已经实际运行验证过
- 低风险改动，已经有测试覆盖，Claude 也审查过

发起审查时总是用 `--brief` 附上审查说明（改动意图、风险点、审查重点）。不带的话会走 Codex 原生审查，输出是英文，也不受审查要求约束。

审查结果同样要甄别：Codex 指出的问题逐条核实，确实存在的才修；误报直接忽略，在汇报中简要说明。
