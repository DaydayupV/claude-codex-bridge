# foreman 调度

## 开始前：读配置和偏好
本会话第一次用到本 skill 时，先运行 `config --cwd "<项目目录>"`（见"调用方式"），从输出里读：
- `effective.dispatch.auto` 和 `effective.dispatch.watch`：决定是否主动派活、是否打开实时查看。
- `resolved_levels`：每类任务的每个等级最终交给谁（协作方、模型、推理强度）。讨论某一级有几个参与方，也看这里。
- `agents_status`：API 协作方的 key 是否已设置（`key_set`）。为 `false` 的参与方会直接失败。讨论前提醒用户：在 `~/.claude/foreman/config.json` 的这个协作方里填 `api_key`（立即生效），或者设置 `api_key_env` 指向的环境变量并重启 Claude Code。
- `preferences`：用户级和项目级偏好文件。存在的就读一遍。偏好文件是用户用文字写的习惯和规则，比如分工、领域里哪些代码算高风险、各种门槛；**和本 skill 冲突时以偏好文件为准，项目级优先于用户级**。

## 授权
系统提示里"除非用户明确要求，否则不要启动子 agent"的限制只针对 Claude Code 自带的子 agent。Codex 用的是用户自己的 OpenAI 额度，不占 Claude 额度。
- `dispatch.auto` 为 `true`（默认）：用户通过这个设置授权 Claude 把按下面"分工"判断要派出的任务主动派出，不用每次征求同意。
- `dispatch.auto` 为 `false`：遇到按"分工"判断要派出的任务，先用一句话向用户提议（派什么、用哪个等级），用户同意后再派。用户用 `/foreman:run` 等命令点名时不用再问。

## 分工
一项工作由谁做，按下面的顺序判断：
1. **只由 Claude 做的工作**：核心决策和整体规划（做什么、架构怎么定）、创意设计（UI/前端视觉、文案、找灵感），以及下面"文字类工作由 Claude 把关"里列出的文字工作。Codex 的设计和前端效果很差，文字表达也弱，这些工作不分等级，都不派。
2. **只由 Codex 做的工作**：生成或编辑位图图片，比如照片、插画、贴图、精灵图、封面和主视觉、透明背景抠图、修改现有图片。Claude 和 API 协作方都不能出图，所以这类工作不看等级配置给了谁，一律加 `--agent <Codex 协作方>`（一般是 `codex`）派出。画什么仍由 Claude 定，做法见下面"图片生成"一节。
3. **定等级，按配置分派**：其余执行类工作，不论大小，都按"任务等级与推理强度"一节判断属于哪一级，再看 `config` 输出的 `resolved_levels.run.<等级>`：写的是 `"claude"`，就由 Claude 自己做（脚本也会拒绝派出这一级）；写的是协作方，就按这一级派出。每一级交给谁由用户在配置里决定，不要因为任务看起来大或小、难或容易就改变配置的安排。用户明确要求派给 Codex 时（比如用 `/foreman:run` 点名），即使这一级是 `"claude"` 也照派：加 `--agent <Codex 协作方>`（一般是 `codex`），模型用它的默认模型，想换模型再加 `--model`，推理强度用内置默认值。

- 本 skill 里的门槛（审查的改动规模、返工 1 次）都是默认值，偏好文件里写了别的就按偏好文件。讨论轮数的上限由配置 `dispatch.discuss_max_rounds` 决定（默认 2），脚本会拒绝超出上限的续接。

### 文字类工作由 Claude 把关
Codex 的文字表达弱，经常不说人话：术语堆砌、翻译腔、绕来绕去，读的人看不懂。凡是给人读的文字，都由 Claude 负责：
- **Claude 自己写，不派**：README、使用说明、设计文档、报告和总结、用户可见的界面文案。这类工作以文字为主，派出去再返工反而更费事。
- **派活前在任务说明里规定好**（写进"命名与文字"一节）：
  - 新增的文件、模块、类、函数、关键参数和配置项叫什么名字，直接给出名单；名单之外的沿用项目现有风格。
  - 注释写在哪里、写什么，语言用中文还是英文与项目保持一致。
  - 日志、报错信息、命令行帮助、输出表头这类会给人看的文字，给出原文或模板，要求照抄。
- **验收时复核**：命名是否直白、前后一致；注释和提示文字能否一眼看懂，有没有啰嗦、翻译腔、过度注释。不合格的小地方 Claude 直接改，不必返工；文字问题多的，在返工说明里给出改好的原文。
- **向用户转述**：Codex 的报告、审查意见和遗留问题，由 Claude 理解后用人话转述给用户，不要原样转贴。

### 图片生成
- **范围**：只限位图。图表、流程图、图标、SVG 矢量图，以及用 HTML、CSS 或 canvas 能画出来的东西都不算，照上面第 1、3 条处理。
- **画什么由 Claude 定**：主体、风格、构图、尺寸和用途由 Claude 写进任务说明；图上要有文字的，给出原文、要求照抄。Codex 只负责出图。用户没要求多张变体时，只出一张。
- **等级**：出图质量取决于图像模型，和推理强度关系不大，一般用 `simple`。同一个任务还要改代码（比如把图接进页面）时，按代码部分定等级。
- **任务说明**：要求用 Codex 内置的 `image_gen` 工具出图，不许改用脚本、SVG 等其他方式代替；写明每张图保存到项目里的路径和文件名。Codex 生成的图先存在 `~/.codex/generated_images/<会话 id>/`，在工作目录外，复制进项目后改动追踪才看得到。
- **验收**：结果里的 `generated_images` 列出这一轮 Codex 生成的图片原文件（完整路径，续接时只列这一轮新出的）。先核对张数；没有这个字段说明这次没有调用出图工具，图是别的办法做的，要返工。再对照 `changes` 确认图已复制到指定位置，然后用 Read 打开亲眼看，核对主体、风格、构图和图上的文字。不合格用 `resume` 返工，在返工说明里写清要改哪里。
- 出一张图要几十秒，这段时间实时查看停在上一步是正常的；图生成后时间线上会出现一行"生成图片 …"。

## 调用方式
唯一入口是本 skill 目录下的 `scripts/bridge.mjs`（即 `${CLAUDE_PLUGIN_ROOT}/skills/dispatch/scripts/bridge.mjs`）。不要手敲 `codex exec`。

- **没有例外**：测试、验收、试跑、一次性问答，也都必须走这个脚本。只读的问答用 `discuss`。插件带有钩子，直接调用 `codex exec` 或 `codex review` 的命令会被拦下。
- **遇到沙箱问题时停下来**：Codex 因为沙箱无法启动命令或报错时，把错误原文和你的判断告诉用户，由用户决定是否修改配置。不要自己换沙箱、改配置文件，也不要想办法绕开脚本。

```bash
node "<脚本路径>" run    --cwd "<项目目录>" --brief "<任务说明.md>" --title "<短标题>" --level <simple|normal|complex> [--add-dir "<目录>"] [--track "<路径>"] [--group <组名> --scope "<路径>"] [--timeout 分钟]
node "<脚本路径>" resume --run <run_id|last> --brief "<返工说明.md>" --level <simple|normal|complex> [--track "<路径>"] [--file "<路径>[:起始行-结束行]"]
node "<脚本路径>" discuss --cwd "<项目目录>" --brief "<议题.md>" --title "<短标题>" --level <simple|normal|complex> [--agent <协作方>] [--file "<路径>[:起始行-结束行]"] [--group <组名>]
node "<脚本路径>" review --cwd "<项目目录>" [--uncommitted | --base <分支> | --commit <sha>] [--brief "<审查重点.md>"] --level <simple|normal|complex>
node "<脚本路径>" status [--run <run_id|last> | --group <组名>] [--limit n]
node "<脚本路径>" watch  [--run <run_id|last> | --group <组名>]
node "<脚本路径>" config [--cwd "<项目目录>"]
node "<脚本路径>" check  [--agent <协作方>]
node "<脚本路径>" await-busy (--group <组名> | --run <run_id>) [--after 分钟]
node "<脚本路径>" cancel --run <run_id>
```

- `check` 检查环境能不能用：Node.js、Git、Codex（能否启动、是否已登录），每个 API 协作方（key 是否设置，并发一个很小的请求确认能连通），以及每个 opencode 协作方（opencode 能否启动、`opencode models` 里有没有这个模型、发一个很小的请求确认能用）。Codex 是必需的，`codex.ok` 为 `false` 时插件不能用；API 和 opencode 协作方是可选的，不通过只影响它参加讨论。每项不通过时，结果里的 `fix` 写明该怎么处理，转告用户即可。派活或讨论因为环境问题失败（找不到 codex、没登录、API 报 401 等）时，先跑 `check` 确认原因。

- 交给谁、模型、推理强度、沙箱、审批、超时由配置文件决定（见"配置"一节）；Codex 没有配置的项沿用它自己的 `~/.codex/config.toml`。
- `--agent <协作方>` 指定这次交给配置 `agents` 里的哪一方。不写时用这一级配置的那一方；讨论的某一级有多个参与方时必须写。目前 API 协作方（如 DeepSeek）和 opencode 协作方只能参加 `discuss`。opencode 协作方也只能通过本脚本调用，不要直接运行 `opencode run` 让它参加讨论。
- 拿不准当前设置时先运行 `config --cwd "<项目目录>"`，它会列出实际生效的配置、记录目录和 watch 启动器的路径。
- 沙箱不是 `read-only` / `workspace-write` 时（比如 `danger-full-access`），`--cwd` **不限制写入范围**，范围只能靠任务说明约束，再靠事后审查 diff 把关。
- 允许改动的范围里有被 `.gitignore` 忽略的路径（比如 `tests/`、结果目录）时，用 `--track "<路径>"` 指定（可以给多次），否则改动追踪看不到这些文件。续接时沿用上一轮的 `--track`。
- 任务说明先写成 UTF-8 文件（有 scratchpad 目录就放在那里，否则放在系统临时目录），脚本会自动附加固定约束：不越界、开工前预检、什么情况下停下来提问、只写必要测试、不 commit/push、不碰密钥、按 schema 汇报。
- **一律用后台方式运行**（Bash 的 `run_in_background`），跑完会自动通知。等待期间可以做别的，不要轮询。
- **每次调用（`run`、`resume`、`discuss`、`review`）都必须在对话里明确告诉用户用的是哪个模型、推理强度多少**，例如"已派出：gpt-6-astra（Codex CLI，effort max），等级 complex"；多方讨论时逐个写出，例如"已发起讨论：gpt-6-astra（Codex CLI，effort max）、deepseek-v4-pro（API，effort max）"。以脚本启动时输出的第一行（"<模式> 开始｜<模型>（<接入方式>，effort …）｜等级 …｜记录目录 …"）为准，不要凭配置自己推断；模型来自 Codex 配置时照实说明。最终汇报里再写一次。
- **启动 `run`、`discuss`、`resume` 后，下一步必须立即处理实时查看**（见"实时查看"一节），测试和小任务也不例外。用户要靠它看到 Codex 在做什么，漏掉就等于让用户干等。
- 结果以 JSON 打印到 stdout，主要字段：
  - `report`：Codex 的结构化报告。
  - `changes`：脚本追踪到的工作目录内改动。每个文件标有 `by`：`agent` 表示有证据是执行的协作方改的（改名前的记录里写作 `codex`），`unknown` 表示归属未知。
  - `notes`：提示信息，比如归属未知的改动、Codex 报告了但没追踪到的文件。
  - `session_id`、`run_dir`：完整 diff 在 `run_dir/diff.patch`。
  - token 消耗：`usage` 是本次调用的输入、缓存、输出 token（`usage_scope` 为 `session_total` 时是整个会话的累计量）；`last_request` 是最近一次请求的用量和模型上下文窗口；`rate_limit` 是 Codex 额度的已用比例。
  - `agent`：这次交给了哪个协作方。API 和 opencode 协作方的结果没有改动追踪（`changes.available` 为 `false`）；API 协作方的 `files` 列出附带了哪些文件，opencode 协作方多一个 `cost_usd`。
- 多个任务可以并行，但文件范围不能重叠，见"并发拆分"一节。**Codex 正在改的文件，Claude 不碰。**

## 配置
用户配置是 `~/.claude/foreman/config.json`，项目配置是 `<项目目录>/.claude/foreman.json`，后者覆盖前者。各字段的含义和默认值见 `references/config.md`，用户问到或要改配置时再读。
- 脚本输出"首次使用，已生成配置文件"时，告诉用户生成了配置文件、在哪里、用了哪些模型，并建议运行 `/foreman:setup` 检查环境、按需添加其他模型参加讨论。
- 脚本输出"已把配置文件 … 改成新结构"时，告诉用户：插件升级后配置文件换成了新的写法（dispatch / agents / levels），设置的内容没有变，原文件备份在哪里。
- **Windows 上不要把 `sandbox` 设成 `read-only`**：Codex 的 Windows 沙箱在只读模式下可能连读文件的命令都启动不了。讨论和审查的只读要求靠脚本附加的规则约束，脚本事后也会检查有没有文件被改动。
- 用户要改配置时，直接编辑对应的 JSON 文件，改完运行 `config` 确认生效。

## 实时查看（每次派活都做）
用后台方式启动 `run`、`discuss` 或 `resume` 之后，立即让用户能看到实时进度。`dispatch.watch` 为 `off` 时跳过本节，只告诉用户可以用 `/foreman:watch` 查看。

- **有 `run_in_terminal` 工具时**（Claude 桌面版），在用户的终端面板里打开：用 `run_in_terminal` 运行 `node <记录目录>/watch.mjs --run <run_id>`，标题写"<模型>：<短标题>"，比如"gpt-6-astra：<短标题>"。多方讨论用同一个组，只开一个标签页：`node <记录目录>/watch.mjs --group <组名>`，标题写"讨论：<短标题>"。记录目录默认是 `~/.claude/foreman/runs`，在 Windows 上写成 `C:\Users\<用户名>\.claude\foreman\runs`，以 `config` 的输出为准。这个启动器由脚本自动生成，插件路径含非 ASCII 字符时也能满足 `run_in_terminal` 只接受 ASCII 的要求。`config` 输出里 `watch_launcher_ascii` 为 `false` 时（记录目录路径含中文等非 ASCII 字符），`run_in_terminal` 会拒绝这条命令：改为把命令放在代码块里发给用户，请用户在自己的终端里运行，并转告 `check` 输出里 `watch.fix` 的处理办法。
- run_id 在启动后后台输出的第一行（"记录目录 …/<run_id>"）里。不加 `--run` 时它会跟踪正在运行的任务，但其他会话可能也在跑任务，所以尽量指定。
- 打开后紧接着把终端面板切到这个标签页，让用户直接看到：调用显示面板的工具（Claude 桌面版里名字带 `show_pane`，可能要先用 ToolSearch 加载），`pane` 填 `terminal`，`tab_id` 填刚才的 tab_id。只开标签页的话，终端面板可能藏在别的面板后面，用户看不到。没有这个工具就跳过。
- 再把标签页链接 `[<标题>](#terminal/<tab_id>)` 发给用户。
- 讨论里有 API 参与方时，同时在后台启动排队检查 `await-busy`（每个组一次；opencode 参与方不需要）。脚本启动时输出的"排队检查"一行给出了完整命令，照着运行即可；它退出后怎么处理见讨论模式里"API 参与方繁忙时"一节。
- **没有 `run_in_terminal` 时**（比如命令行版 Claude Code），把完整的 watch 命令放在 bash 代码块里发给用户，请用户在另一个终端里运行。
- 任务结束后 watch 会自动退出，标签页保留，供用户回看。不要关闭它。
- 退出后的标签页不会再显示新任务。所以每次续接（讨论的下一轮、返工）都要按上面的做法新开一个标签页，不要让用户回上一轮的标签页去看。讨论的下一轮照样用 `--group <组名>`，标题写"讨论：<短标题>（第 N 轮）"，画面里只显示这一轮的参与方。
- 默认是简洁显示。用户要看完整细节时，加 `--verbose`。
- `review` 只在用户要求时才打开实时查看。

## 任务等级与推理强度
`run`、`resume`、`discuss`、`review` 每次都必须显式给出 `--level`，没有默认值，漏写脚本会直接报错。Claude 只判断任务属于哪一级，具体用哪个模型和推理强度由用户在配置的 `levels` 里决定，启动时的第一行会打印实际用的模型和推理强度。用户没写等级或推理强度时，不管是 Claude 主动派活，还是用户用 `/foreman:run`、`/foreman:review`、`/foreman:discuss` 发起，都按下面的标准判断，没有默认等级。

**等级看需要多少判断、出错的代价有多大，不看改动多少**：同样改 20 个文件，照清单机械地改名是 `simple`，改模块之间的接口是 `complex`；只改几行、但根因不明的 bug 也是 `complex`。

执行任务（`run`、`resume`）：

| 等级 | `--level` | 判断标准 | 例子 |
|---|---|---|---|
| 简单 | `simple` | 做法已经确定，几乎不需要判断，结果能逐项核对 | 做法明确的小功能或小脚本、改法已经明确的小修、照现成模式补齐同类代码、按清单批量改名或替换、格式或目录迁移、跑现成脚本整理数据 |
| 常规 | `normal` | 有规格或原因已经清楚，但具体做法和局部细节要自己设计，出错了测试或实际运行容易发现 | 按规格实现功能、写脚本和工具、原因已经清楚但改法要设计的 bug 修复、常规重构、补测试 |
| 复杂 | `complex` | 满足任意一条：根因不明、需要排查；出错了测试不容易发现，后果又重；要改模块之间的接口或约定；性能、并发这类需要反复权衡和验证的 | 根因不明的 bug、金额和计费计算、数据迁移、权限判断、跨模块的接口改动、性能优化、并发 |

审查（`review`）按被审改动的风险定级：
- `simple`：改动量大但很机械，比如批量改名和替换、目录迁移。
- `normal`：一般的功能改动和 bug 修复。
- `complex`：高风险代码（金额和计费、数据删除和迁移、并发、鉴权和安全、不可逆操作），或者根因不明的修复。

讨论（`discuss`）按议题定级：
- `simple`：一次性问答，核对一个事实或对某段代码的理解，不需要比较方案。
- `normal`：有几个方案要比较，但影响范围有限，选错了容易改。
- `complex`：同时满足"讨论模式"里自动开启的三条（复杂、不确定、选错代价高）；结论落地前的证据审查也用这一级。

- 拿不准时往高一级选。
- 用户点名要某个推理强度（比如"用 ultra 跑"）时，改用 `--effort <强度>` 直接指定，不再按等级换算，模型用这个协作方在 `agents` 里的默认模型（不写 `--agent` 时是 Codex）。`--level` 和 `--effort` 只能给一个。
- 用户点名要某个模型时，加 `--model <模型>`，它覆盖配置里的模型，可以和 `--level` 或 `--effort` 一起用。
- 续接时模型按新给的等级重新确定，所以返工升级时可能换成另一个模型；配置里哪里都没写模型时，沿用上一轮的模型。

## 写任务说明
说得越细，Codex 做得越好。按下面的结构写：

```markdown
# 目标
要做成什么，为什么做（一两句背景）。

# 范围
- 允许改动：具体文件或目录
- 只读参考：相关文件
- 不要碰：……

# 规模
预计改动多少行、几个文件；这次不需要的东西，比如命令行参数、配置项、兼容旧数据、测试。

# 要求与约束
接口签名、数据格式、要沿用的现有模式和工具函数、性能要求、兼容性等。

# 允许的适配
Codex 遇到这些情况可以直接处理，不用停下来问。比如：
- 指定的测试入口跑不起来时，可以改用覆盖同一批测试的等效入口
- 允许修正某个测试夹具，但不得削弱断言
（没有就写"无"）

# 命名与文字
- 命名：新增的文件、类、函数、关键参数和配置项叫什么名字
- 注释：哪里需要写，写什么
- 提示文字：日志、报错、帮助信息、输出表头的原文或模板（要求照抄）
（任务不涉及这些时可以省略本节）

# 禁止事项
本任务特有的禁区。

# 完成标准
怎样才算做完，需要跑哪些命令验证（给出具体命令）。

# 交付
需要在报告里特别说明的内容。
```

Codex 偏爱做全做重：简单任务也会加参数、配置项、抽象层、兼容分支和大量测试。"规模"一节就是用来防这个的：写明预计的规模和这次不需要的东西，验收时也拿它对照。脚本附加的固定约束里也有"按规模做、只写必要的测试、不要过度防御"，任务特别容易做过头时，在任务说明里再强调一遍。任务说明本身也按规模写，简单任务不要写成长篇。

"允许的适配"按含义授权，不按改动大小：一行改动也可能改变样本外边界、费率或断言。凡是没写进这一节的越界，固定约束都会要求 Codex 停下来，在报告的 `decision_requests` 里提问。可以预见的环境问题（比如项目里有同名的 `tests` 包），提前写进这一节，能少停一次。

## 并发拆分
Codex 任务的等待时间大部分花在模型思考上，跑命令只占一小部分。所以把一个大任务拆给几个 Codex 会话同时做，能明显缩短等待。代价是总 token 更多（每个会话都要各自读一遍背景），Claude 也要多写几份任务说明、多做几次验收。

### 什么时候拆
下面几条**全部满足**才拆，否则派成一个任务：
1. 能拆成 2 份以上、不超过 Codex 的并发上限（配置 `agents.codex.max_parallel`，见 `config` 输出的 `agents_status.codex.max_parallel`，默认 4；其他会话正在运行的 Codex 任务也占名额），每份**写入的文件互不重叠**，而且**不依赖其他份的产出**。
2. 各份之间的接口（函数签名、数据格式、文件路径），Claude 能在派活前定下来，写进每份任务说明。定不下来就不拆。
3. 每份预计都要 10 分钟以上。太小的任务拆开，固定开销比省下的时间还多。

**不拆**：根因不明、需要排查的 bug；要改共用核心文件的重构；前后衔接的研究阶段；需要整体统一设计的工作；本身就是重计算的任务（同时跑会抢 CPU，这种让 Codex 写批量脚本并行跑）。

适合拆的例子：几个互相独立的脚本或模块；接口定好后，一份写实现、一份补测试；按目录分开的批量修改。

### 怎么派
- 每份按自己的难度各自定等级（见"任务等级与推理强度"）。某份的等级在配置里是 `"claude"` 时，那一份由 Claude 自己做，同样不碰其他份的文件；其余几份照常派出。
- 给同组任务起一个组名（英文短标题加日期，比如 `factor-scripts-1013`；同一个对话里每组用不同的组名，不同对话的组名重复没关系，查看时只算当前对话派出的；只能用英文字母、数字和 `. _ -`，实时查看要把它写进终端命令，脚本会拒绝其他字符），每份都用 `run --group <组名> --scope <允许改动的路径>` 派出，`--scope` 可以给多次。同时派出的几份放在同一条消息里，一起在后台启动。
- 脚本会拒绝两种情况：这个协作方正在运行的任务（不分组、不分会话，全都算）已经达到它的上限；和同组正在运行的任务写入范围重叠。被拒绝时按报错重新划分，或者等前面的任务结束再派。
- 每份任务说明除了通用结构，还要写明：
  - 同组的其他任务在做什么、改哪些文件，这些文件不许碰。
  - 共用的接口约定，原文照抄到每一份里。
  - 这一份单独验证的方法。
- 实时查看只开一个标签页：`node <记录目录>/watch.mjs --group <组名>`，标题写"任务组：<组名>"。它在一个窗口里按模型分块，同时显示每个任务最新的几行进度，全部结束后留下汇总。
- 告诉用户这次拆成了几份、各做什么，以及每份用的模型和推理强度。

### 验收
- 每份先按"验收"一节单独验收，不合格的单独返工（resume 沿用原来的组和范围）。
- 全部通过后，Claude 再做一次**整体验证**：把各份合起来跑完整的测试或脚本，因为每份只是单独验证过。
- 汇报时按份列出 run_id 和 token 消耗，再给出合计。

## 研究与分析类任务
研究类任务指结论要靠实验和数据支撑的工作，比如策略和因子研究、数据分析、方案对比实验、性能调查。这类任务的风险不在代码写错，而在结论超出了证据。

### 研究任务说明的检查清单
把研究派给 Codex 时，在上面的通用结构之外，任务说明还要包含下面几项。某一项不适用时，写明不适用和原因，不要直接省略。讨论阶段已经定下的问题和假设，直接写进来，不用重新讨论。
- **问题与假设**：要回答的问题；每条假设和它的判读标准。判读标准事先定好，不能看到结果再改。
- **对照组**：需要哪些对照和基准，各自回答什么问题。
- **稳健性**：怎么检验结论不是某个参数点或某段时间的偶然，比如参数邻域、时间段切分、换起点。
- **混淆因素**：列出可能干扰结论的因素，要求逐项排查或说明为什么不适用。常见的有：资金或规模路径（本金变化、整手限制）、样本曝光（看过结果后再选）、多重检验、幸存者偏差、数据口径变化。
- **统计判断**：怎么判断差异是否显著，比较多组时怎么校正。
- **交付**：每条结论对应的证据（文件、数字、可以复算的方法），以及没能验证的部分。

### 结论落地前的证据审查
研究结论写进长期档案、报告或文档，或者作为定论交给用户之前，不管研究是 Claude 做的还是 Codex 做的，都用 `discuss` 发起一次证据审查（`--level complex`，开新会话，不在做研究的那个会话里自审）：
- 议题说明逐条列出结论，每条附上证据的位置和关键数字。
- 要求各参与方逐条判断：证据够不够支撑这条结论，有没有说过头，有没有没控制住的混淆因素，统计上站不站得住。
- Claude 按讨论模式逐条裁决，修正结论后再写入。已经写进档案的结论被推翻时，以追加修订的方式更正，不改原记录。

## 验收（每次必做）
1. 先看 `status` 和 `report.status`：不是 `completed` 就先读 `open_issues`。
2. 读 `run_dir/diff.patch`，并核对 `changes.files`：
   - 有没有改到范围外的文件；`report.files_changed` 和实际改动是否一致
   - `by` 为 `unknown` 的文件，可能是 Claude 自己、其他会话改的，也可能是 Codex 用命令或脚本写的。先弄清是谁改的，**不要直接还原**
   - 逻辑对不对，有没有过度防御、多余抽象、冗余测试
   - **有没有做过头**：实际改动明显超过"规模"一节的预计（比如两倍以上），或者出现了没要求的参数、配置项、抽象层、兼容分支、测试。小处 Claude 直接删减；多的话用 resume 返工，在返工说明里列出要删掉的东西
   - 命名、注释和提示文字是否符合任务说明，是否说人话（见"文字类工作由 Claude 把关"）
   - 只追踪工作目录内的改动；如果任务涉及工作目录外的路径，要另外检查
3. **实际运行验证**：跑构建、测试或脚本本身，不能只看 Codex 自己说"通过了"。
4. 确认无误后再向用户汇报。

## 返工与失败
- 不合格时用 `resume` 返工一次，在返工说明里写清楚哪里不对、要怎么改。原因是任务难度估低了的话，返工时把等级升一级（simple → normal → complex）；升上去的那一级在配置里是 `"claude"` 时不再续接，由 Claude 自己接手。其余情况沿用原来的等级。
- 返工后还不合格，或者 Codex 超时、报错，由 Claude 自己接手完成，并告诉用户原因。
- 结果状态为 `stalled`（卡死：超过 `dispatch.stall_min` 分钟没有任何活动，且没有命令在执行，脚本已自动终止；分钟数以 `config` 输出为准）时，多半是网络或服务的临时问题。用 `resume` 让它从断点继续一次；再卡死就由 Claude 接手。可以用 `--stall <分钟>` 调整阈值，`--stall 0` 关闭检测。总超时是 `dispatch.timeout_min`，用 `--timeout` 调整。
- 怀疑任务卡住时，先运行 `status` 看"最后活动 X 分钟前"和当前步骤，不要凭感觉判断。正在执行命令（比如跑大计算）时，长时间没有新事件是正常的。`interrupted` 表示调度进程已经不在了（比如会话或应用被关闭），这时 Claude 收不到完成通知，需要手动查看 `status --run <run_id>`，再决定是续接还是重来。
- `report.status` 为 `blocked` 时，读 `report.decision_requests`，逐条判断：在用户已有授权内、Claude 能决定的，写明决定后用 resume 继续；需要用户决定的，把问题、选项和 Claude 的推荐交给用户。这种为了回答问题的续接不算返工次数。
- 结果状态为 `quota_exhausted` 时，是额度用完了：Codex 是订阅额度，API 协作方是账户余额不足。不要重试，也不要自动改由 Claude 重做；告诉用户额度用完和预计恢复时间（`quota_resets_at`），由用户决定是等额度恢复后用 resume 继续，还是改由 Claude 接手。
- Claude 接手或用户决定放弃的任务，状态是 `interrupted`、`stalled`、`timeout` 或 `quota_exhausted` 时，运行 `cancel --run <run_id>` 标记为已处理：会话开始时的提醒只列还没处理的执行任务。
- 会话开始时的提醒如果列出了执行没有正常结束的任务，在合适的时候告诉用户一句，按用户的意思处理。

## 讨论模式（/foreman:discuss）
遇到复杂的计划、方案或想法时，先和其他模型讨论，不执行。参与方由配置 `levels.discuss.<等级>` 决定：可以只有 Codex，也可以加上 API 协作方（比如 DeepSeek）和 opencode 协作方，几方同时给意见。**观点始终由 Claude 主导**：各参与方的意见只作参考，接受还是拒绝由 Claude 根据论据决定，不因为谁坚持就让步，也不按多数票。

### 什么时候自动开启
用户用 `/foreman:discuss` 发起，或者明确要求和 Codex 或其他模型讨论时，直接开。自动开启必须**同时满足**下面三条，只满足一两条的不开：
1. **复杂**：涉及架构或多个模块，影响长期结构；或者是金额计算、数据一致性、权限和安全等关键逻辑的设计。
2. **不确定**：没有明显的最优解，有好几个可行方案需要权衡；或者关键假设还没验证。
3. **选错代价高**：选错了要大面积返工，或者会影响结果的正确性。

**用户只是来要建议、还没决定做不做时，同样按这三条判断。** 比如"有什么研究方向的建议""这个架构该怎么选"：满足三条就先讨论，再把裁决后的结论交给用户，不要自己直接给出答案。为了写议题说明，可以先读代码和数据、做只读的统计，把事实弄清楚。

普通的实现细节、已经有明确方案的任务、用户已经拍板的决定，都不开。自动开启时告诉用户一句，例如："这个问题我先和其他模型讨论一下。"

### 三类参与方
- **Codex**：能自己读代码、跑只读命令来核实。
- **opencode 协作方**（配置里 `type` 为 `opencode` 的，比如 `opencode-go/glm-5.3`）：通过本机的 opencode CLI 调用模型。脚本只给它读文件、搜索和列目录的工具，它能自己翻项目里的代码，但不能运行命令，也不能改文件。所以：
  - `--file` 和 Codex 一样只列成"重点文件"，不附内容。它只能读项目目录里的文件，项目外的材料要摘进议题。
  - 它每读一次文件都多一次请求，比 API 协作方费额度。订阅额度紧的高档模型（比如 OpenCode Go 里的 Kimi K3、Qwen Max）放在 `complex` 级用。
  - 结果里的 `cost_usd` 是这一轮按厂商价格折算的费用，OpenCode Go 的额度就按这个扣，汇报 token 时一起写上。
  - 它对代码的说法，同样要核实后才能采信。
- **API 协作方**（配置里 `type` 为 `openai-compatible` 的，比如 DeepSeek）：只看得到议题和附带的材料，自己翻不了代码。所以：
  - 用 `--file "<路径>"` 把相关文件附上，可以给多次；`--file "<路径>:<起始行>-<结束行>"` 只附一段。议题里提到的代码、要讨论的核心模块都要附。材料总量有上限（约 30 万字符），超了脚本会报错，这时精选文件或改用行范围。脚本还会自动附上项目文件清单。
  - 附带的材料会发给对应厂商。偏好文件或项目配置不让发的项目，不加 API 协作方。
  - 它对代码的说法，Claude 要对照原文核实后才能采信。
  - 它在 `open_questions` 里要求看的文件，下一轮用 `--file` 补上。
- 给 Codex 和 opencode 协作方也传同样的 `--file` 时，脚本只把路径列成"重点文件"，不附内容，它们会自己去读。

### 流程（轮数上限见配置 `dispatch.discuss_max_rounds`，默认 2）
1. **第 1 轮，独立出方案**：议题说明只写背景、要解决的问题、约束、已知事实、相关代码位置，以及要回答的具体问题，**不写 Claude 自己的倾向**，以免参与方顺着说。在读任何参与方的结果之前，Claude 先把自己的方案写进一个文件（scratchpad 目录或系统临时目录），以免反过来被带偏。然后按 `config` 输出的 `resolved_levels.discuss.<等级>`，给每个参与方各发一次 `discuss`：同一份议题、同一个 `--group`（英文短标题加日期，比如 `config-rework-1013`；同一个对话里每场讨论用不同的组名，后续轮次沿用），每次用 `--agent <名字>` 指定参与方，放在同一条消息里一起在后台启动。这一级只有一个参与方时可以不写 `--agent` 和 `--group`。
2. **第 2 轮，交叉挑错**：各方方案（包括 Claude 的）有实质分歧，或者某一方的结论里有 Claude 还没核实、又会影响结论的地方时才做；基本一致时直接裁决。把各方方案匿名成"方案 A / 方案 B / …"，用 `resume --run <这一方第 1 轮的 run_id>` 分别续接每个参与方（同样放在同一条消息里并行），要求它找出其他方案最薄弱的地方，并和自己的方案对比。只发方案摘要和分歧点，不发完整报告。同时 Claude 也写出对各方方案的质疑。
3. **第 3 轮及以后（可选）**：只有关键分歧还没解决、多一轮确实可能改变结论，并且没有超过 `dispatch.discuss_max_rounds` 时才做。脚本拒绝续接时，就按已有结果裁决。
4. **Claude 裁决**：逐条决定接受还是拒绝各参与方的观点，写明理由，形成最终方案。按证据、约束和可逆性判断，几方一致的结论也可能一起错。

- **`simple` 级（一次性问答）从简**：不用先写自己的方案，不做第 2 轮，也不写决策记录；核实参与方的回答后，用人话直接告诉用户结论和依据。附带文件、实时查看和繁忙处理照常。
- 等级按"任务等级与推理强度"一节里讨论的标准选；自动开启的讨论都满足那三条，用 `complex`。续接下一轮时沿用第 1 轮的等级。
- 每个参与方单独一个 run_id，轮数上限对每个参与方各自生效。每个参与方各占自己协作方的一个并发名额；某一方因为达到并发上限被拒绝时，等它正在运行的任务结束后再补发这一方，不要跳过。
- 某个参与方失败（比如余额不足 `quota_exhausted`、接口报错、key 没设置、被用户终止 `cancelled`）不影响其他参与方：告诉用户哪一方失败、原因是什么，用其余参与方的结果继续。不要为了凑齐参与方去改配置。
- 讨论是只读的：Codex 可以读代码、跑只读命令来支撑观点，但不能改文件。`warnings` 里报出 Codex 改了文件时，检查 diff，还原 Codex 改的部分。`notes` 里归属未知的改动不要还原，多半是别人改的。API 和 opencode 协作方改不了文件。
- 讨论同样要处理实时查看。

### API 参与方繁忙时问用户要不要终止
API 协作方的服务繁忙时，请求会在服务端排队，迟迟不开始处理，最后可能被服务端断开。别让用户干等：
- 发起（或续接）的讨论里有 API 参与方，并且 `config` 输出的 `effective.dispatch.busy_ask_min` 大于 0 时，紧接着在后台再启动一次 `await-busy --group <组名>`（这一级只有一个参与方、没用组时用 `--run <run_id>`）。它不发请求，只在有参与方排队超过 `busy_ask_min` 分钟、或者全部结束时退出，退出时会通知你。
- 它退出后读输出：`busy` 为空就不用管。不为空时，用提问工具问用户，每个排队的参与方一个问题，写明模型和已经排队多久，三个选项：
  - **终止，用其他参与方的结果继续**（推荐）：运行 `cancel --run <run_id>`。这一方的结果标为 `cancelled`，裁决时说明少了它。
  - **再等 5 分钟**：后台再启动 `await-busy --run <run_id> --after <已排队分钟数 + 5>`。
  - **一直等**：不再启动 `await-busy`。
- 用户也可以在实时查看里对排队中的模型按 x 终止，效果和 `cancel` 一样。收到 `cancelled` 的结果时照常继续。
- 需要用户决定的问题，比如偏好、业务取舍、风险承受度，不要替用户拍板，把选项和 Claude 的推荐一起交给用户。

### 向用户汇报：决策记录
不贴原始对话，用人话整理成下面的格式（`simple` 级的问答不用）：
- **议题**：一句话
- **候选方案**：Claude 的和每个参与方的，各自的核心思路和取舍
- **各参与方的主要观点**：按参与方分开列，用模型名称呼（比如 gpt-6-astra、deepseek-v4-pro），每条注明 ✅ 接受 / ❌ 拒绝 / ⚠ 部分接受，并写明理由
- **最终方案**：以及和 Claude 最初方案相比改了什么
- **待确认**：需要用户拍板或先验证的事
- 附上每个参与方的 run_id、模型、推理强度和 token 消耗，方便用户回看原始记录

## 何时请 Codex 审查（/foreman:review）
用户明确要求时直接做。否则按任务情况判断：

**值得审查**
- Claude 自己做的复杂改动（相当于 `complex` 级，包括配置里这一级交给 Claude 的情况），交付前用另一个模型做独立复核
- 高风险代码：金额和计费计算，数据删除和迁移，并发，鉴权和安全，不可逆操作
- 改动大（大约超过 300 行或 5 个以上文件），或者修了一个根因不明的 bug
- 研究结论写进档案或报告之前：用 `discuss` 做证据审查，见"结论落地前的证据审查"
- Codex 交付的高风险改动：用 `review` 发起一个**新会话**审查，不要让它在原会话里自己审自己

**不必审查**
- 小改动、文档、注释、样式、文案、纯配置
- 一次性脚本、原型，且已经实际运行验证过
- 低风险改动，已经有测试覆盖，Claude 也审查过

发起审查时总是用 `--brief` 附上审查说明（改动意图、风险点、审查重点）。不带的话会走 Codex 原生审查，输出是英文，也不受审查要求约束。

审查结果同样要甄别：Codex 指出的问题逐条核实，确实存在的才修；误报直接忽略，在汇报中简要说明。

## 向用户汇报
说明哪些部分是 Codex 或其他协作方做的（附 run_id，以及每次调用的协作方、模型和推理强度，以结果里的 `agent`、`model_shown` 和 `effort` 为准）、每次调用的 token 消耗（本次的输入和缓存比例、输出；`usage_scope` 为 `session_total` 时注明是会话累计）、Claude 审查了什么、怎么验证的、是否请 Codex 做了审查及结果，以及遗留问题。
